**Title:** Real-Time Currency Conversion & Audit Trail

**Business Idea:** Treasury operations teams at our enterprise customers
currently convert currency using manual lookups against a third-party
portal — slow, and it leaves no record for compliance. We need instant,
self-serve conversion inside our own app, and because these are regulated
transactions, every conversion must be reconstructable for an auditor on
demand, not pieced together afterward from emails or spreadsheets. 

**Persona:** Treasury operations analysts at enterprise customers, who
process multiple cross-border settlements a day and are personally
accountable if a conversion can't be justified during an audit.

**User Need:** See a trustworthy converted amount the moment I enter it
— and be able to pull up any past conversion, with its rate and timestamp,
the moment an auditor asks for it.

**Known Constraints:**
- Frontend must read `VITE_API_URL` dynamically at container runtime using
  a generic entrypoint script placeholder replacement; replace the placeholder token
  `__VITE_API_URL__` inside the built `index.html` (or equivalent) with the runtime
  `VITE_API_URL` value.
- Backend must read database configurations exclusively from runtime
  environment variables.
- Backend must query external currency conversion data exclusively using a base URL from an environment variable (`CURRENCY_API_BASE_URL`), defaulting to an unauthenticated open-source endpoint like Frankfurter (`https://frankfurter.dev`).
- The application must not hardcode third-party API response schemas; utilize flexible JSON property mapping or an abstraction layer to isolate internal compliance tracking from external JSON structure changes (such as `rates` vs `conversion_rates`).
- The audit trail record must capture the exact execution timestamp generated by your backend server alongside any date or sequence markers returned by the external provider, ensuring complete sub-second audit reconstruction even if the provider only exposes a calendar date.
- External HTTP calls must handle failures gracefully with fallback values or clear domain exceptions rather than bubbling up raw network or serialization errors.
- CI/CD pipeline must inject placeholders safely at deployment time without
  exposing sensitive data in container layers.
- Restricted to specific stack versions: React (Vite/Node 24.*) and C#
  (**backend must target `net10.0` for build/test; CI must use `dotnet-version: 10.0.x`**).
- Must adhere to a strict folder layout (`src/frontend` and `src/backend`).
- A .NET solution file must always be generated at `src/backend/OuterloopLabApi.sln` via `dotnet new sln` + `dotnet sln add`, with the backend project added to it, and CI/build/test commands must invoke this `.sln` rather than the `.csproj` directly.
- Deploy as a single Azure Container App using the sidecar pattern to host
  both frontend and backend.
- Authenticate to Cosmos DB exclusively using token-based authentication via the pre-assigned User-Assigned Managed Identity, instantiated using `DefaultAzureCredential` configured with the specific `ManagedIdentityClientId`. Absolutely zero connection strings, master keys, or account keys are permitted in code, configurations, or logs.
- Utilize `Microsoft.Azure.Cosmos` and `Azure.Identity` packages for
  secure, token-based database interactions, including data-plane CRUD operations like adding and deleting items.
- Include `Azure.ResourceManager` and `Azure.ResourceManager.CosmosDB` packages to programmatically provision the Cosmos DB database and container via the control plane inside the application startup lifecycle (`Program.cs`) before the web application runs, utilizing the same token-based Managed Identity credentials for authentication.
  - ARM provisioning is best-effort; Managed Identity RBAC for ARM may differ from data-plane RBAC.
  - CRUD (and data-plane creation if needed) must be done via the Cosmos SDK (data-plane) using token-based Managed Identity credentials; access keys must not be used.
  - After ARM attempt, startup must run token-authenticated data-plane `CreateDatabaseIfNotExistsAsync` and `CreateContainerIfNotExistsAsync` and only proceed if the database/container are available (either already exist or were created). If token-authenticated data-plane create-if-not-exists fails, startup must fail.
- Map and bind all configuration values, including `AZURE_MANAGED_IDENTITY_CLIENT_ID`, endpoint URLs, and resource names, directly from the environment variables **using the exact keys** defined in `docs\CONTAINER_ENVIRONMENT_VARIABLES.md` without using local settings configuration files as fallbacks.

**Current Context:** `src/backend/OuterloopLabApi.sln` is the required .NET solution entrypoint. Assume the backend project is located at `src/backend/OuterloopLabApi/OuterloopLabApi.csproj` with startup in `src/backend/OuterloopLabApi/Program.cs`; if the project folder name differs, apply the same changes in the actual backend project under `src/backend` while keeping it added to `src/backend/OuterloopLabApi.sln`. The frontend runtime configuration touchpoint is `src/frontend/index.html`, and the primary UI entrypoints are assumed to be `src/frontend/src/main.tsx` and `src/frontend/src/App.tsx`. New feature code should be added beneath `src/backend/OuterloopLabApi/Controllers`, `src/backend/OuterloopLabApi/Services`, `src/backend/OuterloopLabApi/Models`, `src/backend/OuterloopLabApi/Data`, and `src/frontend/src/` using feature-focused files for API calls, form state, and audit result rendering.

**In Scope:**
- Add a backend API endpoint to perform a live currency conversion for a requested amount, source currency, and target currency.
- Add a backend API endpoint to retrieve a previously saved conversion audit record by its server-generated identifier.
- Normalize the third-party currency provider response into an internal model that captures rate, converted amount, provider date/sequence marker, and backend execution timestamp.
- Persist one audit document per successful conversion in Cosmos DB so the same record can be reconstructed later without recalculating it.
- Add frontend UI in `src/frontend` for entering amount/from/to currencies, showing the returned converted result immediately, and looking up a prior audit record by identifier.
- Add validation for positive numeric amounts and three-letter currency codes before submitting requests.
- Add automated tests covering at least successful conversion persistence and graceful handling of upstream provider failure.

**Out of Scope:**
- User authentication, authorization, or per-user audit partitioning rules.
- Batch conversion uploads, CSV import/export, or spreadsheet-style workflows.
- Historical charting, rate trend analytics, or scheduled/background refresh of exchange rates.
- Manual editing or deletion of audit records after they are stored.
- Infrastructure creation outside the application startup behavior already required by Known Constraints.

**Feature Constraints:**
- Use `IHttpClientFactory` for the outbound currency provider integration, with a dedicated adapter/service that returns an internal normalized result rather than exposing raw provider JSON directly to controllers or frontend code.
- Use `decimal` for money amounts and exchange rates in backend request/response models and persistence models; round the displayed converted amount to 2 decimal places using midpoint rounding away from zero for consistency.
- Generate the audit identifier on the backend (for example, a GUID string) and return it in the conversion response so the frontend can immediately use it for later lookup.
- The frontend must never calculate the converted amount locally; it must always display the value returned by the backend response.
- Persist successful conversion records only after the provider response has been normalized and validated; failed provider calls must not create partial audit documents.
- Return domain-friendly `ProblemDetails` responses for validation errors and upstream provider failures, without leaking raw exception messages, stack traces, or provider-specific serialization details.

**Expected Outcome:** A user can submit a conversion request from `src/frontend`, receive an immediate converted result from `src/backend`, and later retrieve the exact persisted audit record by identifier. Sample success case: submitting `POST /api/conversions` with `{ "fromCurrency": "USD", "toCurrency": "EUR", "amount": 100.00 }` when the normalized provider rate is `0.92` and the provider date marker is `2026-08-01` returns HTTP `200` with a payload that includes a backend-generated `conversionId`, `fromCurrency: "USD"`, `toCurrency: "EUR"`, `amount: 100.00`, `rate: 0.92`, `convertedAmount: 92.00`, `providerDateMarker: "2026-08-01"`, and `executedAtUtc` in ISO 8601 UTC format with sub-second precision; the same values are stored in Cosmos DB and `GET /api/conversions/{conversionId}` returns the persisted record without recomputing the rate. Sample failure case: if the upstream provider times out or returns unusable data, the conversion endpoint responds with a `ProblemDetails` payload and HTTP `503` (or another deliberate 5xx/4xx chosen for the failure mode), with a stable domain title such as `Currency provider unavailable`, and no audit document is written for that failed request.

**Expected Agent Output:** A code change set that updates `src/frontend/index.html` and frontend source files under `src/frontend/src/` for conversion entry and audit lookup, adds backend controller/service/provider/repository/model code and startup registration in the backend project under `src/backend`, persists and retrieves audit records in Cosmos DB, and includes automated tests that can be executed through `src/backend/OuterloopLabApi.sln` for successful conversion persistence and graceful provider-failure behavior.

**Suggested Intent For OpenCode:** Implement the feature described in `spec/realtime-currency-conversion-audit-trail.md` and respect every Known Constraint exactly as written, including runtime `VITE_API_URL` placeholder replacement in `src/frontend`, strict use of `src/backend/OuterloopLabApi.sln` with a `net10.0` backend, environment-variable-only configuration, token-authenticated Cosmos DB access and startup provisioning behavior, flexible normalization of third-party currency JSON, and graceful external HTTP failure handling; add a frontend conversion/audit lookup flow, backend conversion and retrieval endpoints, Cosmos-backed audit persistence, and automated tests that verify both the happy path and the provider-failure path.
